## KMD Documentation

### Overview
The KMD (Kotlin Multiplatform Desktop) project includes a data downloader system that fetches geospatial gata from multiple sources: NASA elevation data, FAA obstruction data, and OpenStreetMap aeroway data.

The KMD code has to be run from within the `kmd` folder. As specified in the `README.md` in the `kmd` folder, `/composeApp` holds code shared across multiplatform applications. Currently the only functioning platform is `jvmMain`, which has additional files.
Many of the files in the `kmd` files were generated by JeetBrains when initializing the kmd project.
In `kmd/src/commonMain/kotlin/com/jeetbrains/greeting/App.kt` there is code for users to select the regions that they want to download, which sends their selection choices to `DownloadManager()` in `DownloadManager.kt`, which is then dependent on `kmd/src/jvmMain` since it is desktop specific. The state lat/lon boundaries are listed in `App.kt`.

The installation button just runs the install script and could potentially be taken out as it is pretty easy for a user to already do that.

`jvmMain` has a resources folder for the binaries of the install script. Currently `DownloadManager.jvm.kt` in jvmMain runs go binaries of the go downloader code but a kotlin downloader version is in progress and described below, currently in the `kmd` branch.

### Nasa Earthdata (Elevation Data)
**Purpose:** Downloads NASADEM heightmap tiles for terrain elevation data.

**File:** `nasa.kt`

**Key Functions:**
- `downloadHeightmaps(heightmaps: List<String>, directoryPath: String)` - Downloads NASA elevation tiles
- `heightmapToURL(heightmap: String)` - Converts tile IDs (e.g., "n48w123") to NASA download URLs
- `unzip(zipFile: String, targetDir: String)` - Extracts downloaded zip archives

**Authentication:**
- Requires `EARTHDATA_TOKEN` environment variable
- Token obtained from [NASA Earthdata](https://urs.earthdata.nasa.gov/)

**Data Format:**
- Tile naming: `[ns]DD[ew]DDD` (e.g., "n48w123" = 48°N, 123°W)
- Coverage: 1° × 1° tiles
- Output: `.hgt` heightmap files

### FAA Digital Obstable File (Obstruction Data)
**Purpose:** Processes FAA obstruction data (towers, buildings, etc.) for aviation safety.

**File:** `faa.kt`

**Key Functions:**
- `generateObstructionData()` - Main entry point, downloads and processes FAA data
- `downloadFAADOF(finalPath: String)` - Downloads latest DOF.DAT file from FAA
- `parseDOFFile(filePath: String, squareBuffers: Map)` - Parses fixed-width DOF format
- `saveToProtobufs(squareBuffers: Map)` - Serializes to protobuf format

**Data Format:**
- Input: Fixed-width DOF.DAT file (updated every 56 days)
- Parsing: Column-based extraction of lat/lon, height, type, quantity
- Output: Protocol Buffer `.pb` files per coordinate square

**Update Logic:**
- Checks file currency date from header
- Auto-downloads if file is missing or >58 days old
- Scrapes FAA website for latest release URL

### OpenStreetMap (Aeroway Data)
**Purpose:** Fetches airport infrastructure data (hangars, terminals, towers) from OSM.

**File:** `osm.kt`

**Key Functions:**
- `generateAirData(maps: List<List<Int>>, apiUrl: String)` - Fetches aeroway data for coordinate squares
- `makeAirApiRequest(apiUrl: String, map: List<Int>)` - Queries Overpass API
- `storeAirData(ways: List, nodes: Map, airType: String)` - Converts OSM ways to point lists

**API:**
- Uses [Overpass API](https://overpass-api.de/api/interpreter)
- Queries for `aeroway=hangar|terminal|tower` tags
- Returns JSON with node/way geometry

**Data Format:**
- Input: OSM JSON via Overpass API
- Processing: Resolves way node references, extracts elevation tags
- Output: Lists of `OSMPoint` (lat, lon, height)


### Download Manager
The `DownloadManager` uses Kotlin Multiplatform's `expect`/`actual` pattern:

**`commonMain/DownloadManager.kt`** - Interface definition:
```kotlin
expect class DownloadManager {
    suspend fun downloadData(
        regions: Set<BoundingBox>,
        useNASA: Boolean,
        useOSM: Boolean,
        useFAA: Boolean,
        outputDir: String
    ): Result<String>
    
    suspend fun installScript(): Result<String>
}
```

**`jvmMain/DownloadManager.jvm.kt`** - Desktop implementation:
- Directly calls Kotlin data fetcher functions
- Converts `BoundingBox` to tile coordinates
- Runs downloads on IO dispatcher

**`androidMain/DownloadManager.android.kt`** - Stub:
- Returns failure (downloads not supported on Android)

**`jsMain/DownloadManager.js.kt`** - Stub:
- Returns failure (downloads not supported in browser)

**`wasmJsMain/DownloadManager.wasmJs.kt`** - Stub:
- Returns failure (downloads not supported in Wasm)

#### BoundingBox Extensions

**File:** `DownloadManager.jvm.kt`

**`BoundingBox.toHeightmapTiles()`**
- Converts geographic bounds to NASA tile identifiers
- Enumerates all 1° tiles within the bounding box
- Example: `BoundingBox(48, -123, 49, -122)` → `["n48w123", "n48w122", "n49w123", "n49w122"]`

**`BoundingBox.toCoordinateSquares()`**
- Converts bounds to integer coordinate pairs for OSM queries
- Example: `BoundingBox(48, -123, 49, -122)` → `[[48, -123], [48, -122], [49, -123], [49, -122]]`

### Protocol Buffers Integration

#### Why Protobuf?

The Kotlin implementation uses **the same protobuf schema as the Go codebase** to ensure binary compatibility. This allows:
- Go and Kotlin code to read/write the same `.pb` files
- Efficient binary serialization
- Type-safe data structures
- Cross-language compatibility

#### Setup Process

1. **Proto Schema Files** (from Go project):
   - `faa.proto` - Defines `FAAPoint` and `ObstructionSquare`
   - `road.proto` - Defines road/OSM data structures

2. **Code Generation**:
   ```bash
   # Using protoc 28.3 (must match runtime version)
   protoc --java_out=src/jvmMain/java \
          --proto_path=src/jvmMain/proto \
          src/jvmMain/proto/faa.proto
   ```

3. **Gradle Dependency**:
   ```kotlin
   jvmMain.dependencies {
       implementation("com.google.protobuf:protobuf-java:4.28.3")
   }
   ```

4. **Generated Classes**:
   - `obs.Faa` - Java protobuf classes for FAA data
   - `RoadOuterClass` - Java protobuf classes for road data



## Sensor Documentation
Sensor logic is kept in `internal/camera/sensors.go`, and `internal/camera/hat.py`. The raspberry pi hat has a Python API and since getting the yaw, pitch, and roll from it is simple code that doesn't need to change, so the Python code is simply executed by Go in `sensors.go` under `StartSensors()`, where the data is piped in and applied to the camera. Note that `StartSensors` is activated by the flag `hat`, since the rpi hat returns sensor data. After getting this data from the hat, magentic declination is applied from the World Magnetic Model using the Go package `github.com/westphae/geomag/pkg/wmm` which is a golang implementation of the NOAH WMM. (Necessary for accurate sense of direction due to shifting magnetic fields near the poles). The current data used is the 2025 NOAH WMM data which is valid until 2029, and is stored in `synvis/assets/WMM/WMM2025COF/WMM.COF`.

The GPS logic relies on the https://github.com/stratoberry/go-gpsd library that is a go streaming client for GPSD's JSON service. This library offers difference filters, which allow you to capture only certain types of GPSD reports. We are curently using it with the `TPVFilter`, which is the Time-Positiion-Velocity filter and returns the altitude, latitude, longititude, and if the report has a fix or got a valid value. This is the most standard form of GPSD report, but other report types are available in the `stratoberry` library if deemed useful.

For both `StartSensors()` and `StartGPS()`, they are passed a context so that the functions can be terminated (otherwise they would run in infinite loops). This is because the ui-config menu allows users to toggle using the gps and/or hat on or off. Rather than changing the off mode to simply not update the camera actively, the design decision was made to terminate the process. It may be possible that this design decision will be overturned in the future.

The GPS needs to get a fix before it can begin sending data. If the red light is flashing, then the GPS does NOT have a fix. Getting a fix can take up to 15 minutes, although usually less time if the GPS has recently gotten a fix in that same area. Getting a fix requires the setup to be outside so that it can locate 3-4 satellites. CF inhibits the signal connection.
